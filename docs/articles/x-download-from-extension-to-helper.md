# 从浏览器扩展到 macOS Helper：我如何做出一个真正能工作的 X 视频下载器

一开始，我以为这个项目最简单的形态应该是：浏览器扩展拿到 X 帖子地址，把它交给 `yt-dlp`，然后等待视频出现在下载目录。

这个思路足够自然，也足够错误。

最终完成的 X Download 仍然使用 `yt-dlp` 和 FFmpeg，但它不再让 `yt-dlp` 解析帖子 URL。浏览器扩展负责从当前 X 页面取得真实媒体来源，macOS Helper 只负责下载、合并、进度反馈和文件管理。

这篇文章记录这条架构是怎样形成的，以及过程中几个比代码本身更重要的判断。

## 最初的目标并不复杂

用户打开一篇 X 帖子，点击浏览器工具栏上的 X Download，macOS 菜单栏里出现下载任务，最终视频保存到：

```text
~/Downloads/X Download/
```

目标浏览器只有 Chrome 和 Edge，桌面端只做 macOS。这个范围让技术选择比较直接：

- 浏览器扩展使用 Manifest V3、WXT 和 TypeScript；
- macOS Helper 使用 SwiftUI 和 AppKit；
- 浏览器与本机程序通过 Native Messaging 通信；
- `yt-dlp` 负责媒体下载；
- FFmpeg 负责音视频合并和 MP4 封装。

但我没有一开始就把所有模块连接起来，而是先固定每一层的边界。

## 第一步只是识别当前帖子

扩展的第一版只做一件事：识别当前标签页是不是 X 单帖页面。

它接受这样的地址：

```text
https://x.com/account/status/123456789
```

然后去掉查询参数、锚点和 `/video/1`、`/photo/1` 之类的尾路径，得到稳定的帖子 ID 和规范化地址。

这一版没有 Popup，没有下载，也没有扫描页面 DOM。它看起来离最终产品很远，却建立了后面一直沿用的任务身份：每次点击只针对用户当前明确打开的一篇帖子。

## macOS Helper 为什么使用 Popover

Helper 是一个不显示 Dock 图标的菜单栏应用。AppKit 管理 `NSStatusItem`、`NSPopover` 和应用生命周期，SwiftUI 负责任务列表。

一开始需要决定它究竟是“菜单”，还是“一个从菜单栏打开的小应用”。任务行里要显示帖子、状态、失败详情、按钮和进度，传统 `NSMenu` 并不适合这种布局，所以最终使用一个原生 transient `NSPopover`。

这个选择也确定了整个 UI 的方向：原生、简单、没有额外装饰。点击菜单栏图标打开面板，点击外部或按 Esc 收起，任务状态由应用继续持有。

## Native Messaging 不是直接连接 GUI App

Chrome 的 Native Messaging 会启动一个通过标准输入输出读写协议帧的本地进程，而菜单栏 Helper 是一个长期运行的 GUI App。让同一个进程同时承担这两个生命周期，会让浏览器连接、日志、UI 和任务状态互相干扰。

因此我在中间增加了一个很薄的命令行 Bridge：

```text
Extension
  → Native Messaging
  → XDownloadNativeHost
  → Unix Domain Socket
  → X Download Helper
```

浏览器每次请求启动 Bridge。Bridge 读取一条消息，检查扩展来源和协议版本，通过当前用户的 Unix Socket 转发给 Helper，写回响应后退出。

Helper 如果尚未运行，Bridge 会从自己位于 App Bundle 中的位置找到并启动它。Helper 启动后还会自动刷新 Chrome 和 Edge 的 Native Host Manifest，减少本机开发时的手工注册工作。

Bridge 不理解 X，不保存任务，也不执行下载。它只是把浏览器协议和常驻应用隔开。

## 我不想让用户安装 Homebrew

下载器如果依赖系统里的 `yt-dlp`、Python、Homebrew 或 PATH，很难保证两台机器运行的是同一套工具。

X Download Helper 把固定版本的 `yt-dlp` 和原生 Apple Silicon FFmpeg 放进自己的 App Bundle。构建准备阶段校验来源、SHA-256、版本和架构；应用运行时只接受 Bundle 内的固定路径。

进程启动不经过 Shell，而是使用可执行文件绝对路径和参数数组。`yt-dlp` 固定带上 `--ignore-config` 和 `--no-update`，既不读取用户配置，也不在运行中自行升级。

这比“请先执行 `brew install`”麻烦一些，却使下载行为真正属于应用本身。

## 第一个下载方案为什么失败

最初的下载链路是：扩展发送帖子 URL，Helper 调用 `yt-dlp` 解析帖子，再下载每个视频。

队列、临时目录、FFmpeg 合并和错误反馈都能够工作。真正的问题出现在媒体解析入口。某些帖子在已经登录的浏览器里可以正常播放，但 `yt-dlp` 的游客解析返回：

```text
No video could be found in this tweet
```

这不是“再换一个输出文件名”能够解决的问题。浏览器和 Helper 看到的不是同一个访问环境：页面拥有当前会话，独立本机进程没有。

## 为什么没有把 Cookie 传给 Helper

最直接的补丁似乎是读取浏览器 Cookie。但这会立即带来一组新的问题：

- 当前页面可能来自 Chrome 或 Edge 的任意 Profile；
- macOS 会限制应用读取浏览器数据；
- Cookie 存储和解密方式可能变化；
- Native Messaging 协议开始承载登录凭据；
- 调试日志和错误处理必须承担更多敏感数据风险。

更重要的是，页面已经拥有所需会话。与其把整个会话搬到 Helper，不如只从页面取出下载真正需要的最小信息。

## `blob:` 不是视频地址

检查 `<video>` 元素时，经常会看到：

```text
blob:https://x.com/...
```

它只是当前页面进程里的对象引用，不是公网文件 URL。把它复制给 Helper 没有意义，因为 Helper 不在同一个浏览器进程里。

网络记录里还能看到很多来自 `video.twimg.com` 的 `.m4s`。这些是 DASH 音频或视频分片，单个文件只覆盖一小段时间，而且通常还需要初始化段和清单。它们能证明页面正在播放媒体，却不是完整下载入口。

适合传给 Helper 的应该是完整媒体描述：

- `.mpd`：DASH manifest；
- `.m3u8`：HLS playlist；
- `.mp4`：完整 MP4 variant。

## 让扩展观察页面已经取得的数据

最终方案把媒体解析放回浏览器，但没有去调用一个硬编码的私有 API。

扩展在 `document_start` 注入一个 MAIN world 观察器，包装页面自己的 `fetch` 和 XHR。它只读取候选 API 响应的副本，不修改请求、不重复请求，也不改变 X 页面拿到的响应。

观察器在嵌套响应中寻找当前帖子的 `rest_id` 和视频 `variants`。对于同一个视频，它按以下顺序选择一个完整来源：

```text
DASH → HLS → 最高码率 MP4
```

这里使用 MAIN world，是因为页面的 `fetch` 和 XHR 属于页面自己的 JavaScript 环境。但 MAIN world 的消息不能直接信任，所以还需要隔离世界桥重新校验。

## 跨越每一层都重新验证

隔离世界只接受满足以下条件的数据：

- 媒体属于当前页面的 `postId`；
- URL 使用 HTTPS；
- 主机严格等于 `video.twimg.com`；
- 类型是 HLS、DASH 或 MP4；
- 不是图片、`blob:` 或孤立 `.m4s`；
- 媒体 ID 不重复。

结果只保存在内存中。X 是单页应用，页面切换到另一篇帖子后，旧缓存会被清除；后台真正查询时还会再次比较当前帖子 ID。

用户点击扩展后，Background 最多等待三秒。如果仍没有完整来源，Popup 会明确告诉用户“未获取到可下载的视频来源”，而不是向 Helper 发送一个空任务。

Native Host 和 Helper 不会因为数据来自扩展就自动信任它。Helper 会再次验证帖子地址、媒体数组、URL 域名和文件类型。这种重复不是浪费，而是跨进程边界应该付出的成本。

## `yt-dlp` 还在，但职责变了

页面媒体方案的第一版仍保留旧的帖子 URL 解析作为降级。这是一种看似保险的兼容策略：新路径失败时，还能试试旧路径。

问题在于旧路径已经被实际证明不可靠。保留它只会让一次点击拥有两种完全不同的行为，并把已知失败包装成“备用方案”。

最终版本删除了旧协议和帖子解析器。请求必须使用协议 v2，并携带非空 `mediaSources`。没有媒体来源时，任务根本不会进入 Helper。

`yt-dlp` 并没有被删除。它现在接收的是经过校验的 HLS、DASH 或 MP4 URL，负责下载最高可用质量，并调用 Bundle 内的 FFmpeg 合并或封装。它从“X 帖子解析器”变成了“媒体下载执行器”。

这是整个项目最关键的职责调整。

## 下载目录为什么不直接写临时文件

最终文件保存在：

```text
~/Downloads/X Download/
```

但下载过程不会直接在这里生成 `.part`、音频流、视频流和合并中间文件。每个任务先创建独立工作区：

```text
系统临时目录/x-download/<task UUID>/
```

只有完整结果成功生成后，Helper 才把文件移动到最终目录。同名文件不会覆盖，而是使用 `-1`、`-2` 递增。

任务成功或失败都会清理自己的工作区；Helper 每次启动还会清理上次崩溃、强制退出或断电留下的专属临时目录。这样下载目录只包含用户可以使用的成品，而不是半完成资源。

## 进度条表达的是阶段，不是假精确

任务面板会显示：

```text
准备中
下载视频
下载音频
合并音视频
保存到下载目录
完成 / 失败
```

`yt-dlp` 的结构化进度输出可以给出视频和音频下载百分比。FFmpeg 合并阶段通常没有可靠的总字节比例，所以这里只表达合并开始和结束。

总进度按阶段估算：视频 40%、音频 40%、合并 20%，多视频任务再结合当前序号计算。这个数字不是精确流量统计，但它连续、不倒退，而且能让用户知道任务卡在哪个阶段。

## 最终架构

```text
X 单帖页面
  │
  ├─ MAIN world：观察 fetch/XHR 响应副本
  │
  ├─ isolated world：校验并缓存 video.twimg.com 来源
  │
  └─ Extension Background：等待来源并发送协议 v2
        │
        ▼
  XDownloadNativeHost
        │  Unix Domain Socket
        ▼
  X Download Helper
        ├─ 任务队列与去重
        ├─ 阶段状态和总进度
        ├─ Bundle 内 yt-dlp/FFmpeg
        ├─ 临时任务工作区
        └─ ~/Downloads/X Download/
```

每一层都只有一个主要职责：页面负责暴露自己已经拥有的媒体信息；扩展负责提取和清洗；Bridge 负责通信；Helper 负责执行和文件生命周期。

## 这个方案仍然不完美

已经完成的主路径并不意味着所有问题都消失了：

- X 改变接口响应结构后，媒体提取逻辑可能需要调整；
- `video.twimg.com` 地址可能过期，长时间排队可能导致下载失败；
- 合并进度没有连续的真实百分比；
- 当前“移除”任务不会终止已经启动的本机进程；
- 还没有自动重试、断点续传、任务历史和持久化队列；
- Native Host 仍使用固定开发扩展 ID，尚未进入正式分发阶段；
- 当前只覆盖 Chrome、Edge 和 Apple Silicon macOS。

这些限制不会被旧的帖子 URL 降级掩盖。用户得到的要么是经过验证的媒体任务，要么是明确的来源缺失或下载错误。

## 我从这个项目学到的几件事

第一，下载器最重要的不一定是下载代码，而是输入是否真实可靠。执行链路做得再完整，也不能弥补错误的媒体入口。

第二，认证环境应该尽量留在拥有它的地方。浏览器页面已经有会话，就让页面提取最小结果，而不是把 Cookie 和 Profile 问题复制到桌面应用。

第三，跨进程架构的价值来自职责边界，不来自组件数量。Extension、Bridge 和 Helper 看起来比一个脚本复杂，但每一层都更容易解释、测试和替换。

第四，失败文件的处理和成功下载同样属于产品功能。一个不会清理 `.part` 和中间文件的下载器，即使偶尔能成功，也会给用户留下长期成本。

最后，不应该把已经失败的方案保留成“也许有用”的降级。删除帖子 URL 解析后，系统能力变少了，但行为更确定，架构也更诚实。

X Download 最后不是靠找到一个神奇的 `yt-dlp` 参数完成的。它是在一次次验证中，把解析、通信、执行和文件管理放回最适合它们的位置，才真正从“能写出来”走到了“能工作”。
