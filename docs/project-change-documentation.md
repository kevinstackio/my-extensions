# 项目改造文档规范

## 目标

项目需求、设计、计划、测试和验收记录全部保存在 Git 管理的 `docs/` 目录中，随代码一起维护，不依赖外部任务管理平台。

每一次独立改造使用一个文件夹，文件夹内只保留当前改造真正需要的文档。

## 改造目录

```text
docs/
└─ changes/
   └─ YYYY-MM-DD-<project>-<change-title>/
      ├─ README.md
      ├─ spec.md
      ├─ plan.md
      └─ acceptance.md
```

示例：

```text
docs/changes/2026-09-18-my-tabs-shadcn-ui-migration/
```

目录命名规则：

- 使用创建日期，而不是最后更新时间。
- 项目名使用稳定的小写 kebab-case 名称。
- 改造标题使用简洁的小写 kebab-case 描述。
- 文件夹名称必须同时体现日期、项目和本次改造主题。

## 文档职责

### `README.md`

改造的总入口，记录整体目标和当前状态：

- 工作项 ID
- 改造背景
- 总目标
- 实施范围
- 排除项
- 依赖和风险
- 阶段列表
- 最终验收标准
- 文档导航

README 只描述整体结果，不记录详细的执行过程。

### `spec.md`

记录设计与决策：

- 架构方案
- 模块和组件边界
- 数据流和依赖关系
- Design Tokens 或 API 约束
- 技术取舍
- 兼容性要求
- 已知风险和非目标

设计确认后，除非决策发生变化，不在 `spec.md` 中记录执行过程。

### `plan.md`

记录实施计划和每个阶段的验收标准。每个阶段必须包含：

- 阶段目标
- 实施范围
- 影响文件或模块
- 实施步骤
- 自动化验证
- 阶段验收标准
- 完成条件和停止点

阶段验收标准在计划阶段确定，实际验收结果写入 `acceptance.md`。

示例：

```md
## 阶段 1：统一 Design Tokens

### 目标

完成全局颜色、字体、边框和层级 Token 的统一。

### 实施内容

- 修改全局样式 Token
- 对齐语义化颜色变量
- 保留业务专用 Token

### 自动化验证

- TypeScript
- 业务逻辑测试
- CSS 构建
- WXT production build

### 阶段验收标准

- Token 可以被组件正常引用
- 构建产物包含新的 CSS
- 现有业务逻辑不发生变化
- 视觉效果由用户在 Chrome 或 Edge 中验收

### 完成条件

- 自动化验证通过
- 用户完成视觉和交互验收
- 允许创建阶段 Commit
```

### `acceptance.md`

记录实际测试和用户验收结果，不重复记录计划：

- 自动化验证实际结果
- 用户需要执行的浏览器验收步骤
- 用户确认的视觉和交互结果
- 验收状态
- 验收日期
- 对应 Commit SHA

示例：

```md
# 阶段验收记录

## 阶段 1：统一 Design Tokens

### 自动化验证

- TypeScript：通过
- Vitest：通过
- WXT build：通过

### 用户验收

- Chrome：通过
- Edge：通过
- 深色模式：通过
- Hover 与 Focus：通过

### 结论

- 验收状态：通过
- 验收人：用户
- 验收日期：2026-09-20
- Commit：`abc1234`
```

## 测试与验收边界

自动化测试只验证业务逻辑和代码逻辑，包括：

- 数据转换、过滤、排序和状态流转
- 组件输入输出、事件处理和条件分支
- 类型约束、配置解析和资源完整性
- 构建结果和 CSS 静态结构
- CSS 语法、Token 定义、变量引用和类名生成

需要浏览器渲染后才能确定的内容，由用户在 Chrome 或 Edge 中人工验收，包括：

- 实际颜色、间距、尺寸、位置和层级
- 明暗主题的视觉效果
- Hover、Focus、Active 和 Disabled 表现
- Tooltip、菜单、弹层和指针交互
- 动画、过渡、响应式布局和首屏闪烁

不得通过截图、像素比较、布局测量、模拟指针事件或假 DOM 来替代用户的视觉和交互验收。

## 改造流程

```text
创建改造文件夹
→ README 记录总目标
→ spec 记录设计与决策
→ plan 记录实施步骤与阶段标准
→ 开发和自动化逻辑测试
→ 用户进行视觉与交互验收
→ acceptance 记录实际结果
→ 创建 Commit 并记录 SHA
```

## 工作项 ID 与 Commit

工作项使用项目内编号，例如：

```text
MYTABS-20260918-SHADCN
```

Commit 使用该工作项 ID 作为 footer：

```text
Refs: MYTABS-20260918-SHADCN
```

一个 Commit 只对应一个可独立验收和回滚的阶段。不同类型或不同用户结果必须拆分为多个 Commit。
