## 目标与事实边界

现有扩展能够识别 X 单帖并通过 Native Messaging 唤起 Helper；现有 Helper 能够完成内存队列去重、yt-dlp/FFmpeg 调用、桌面落盘和完整失败反馈。当前缺口只在媒体解析：部分帖子在登录页面中可以播放，但 yt-dlp 游客解析返回 `No video could be found in this tweet`。

页面 DOM 中的 `blob:` 地址仅引用浏览器页面进程里的媒体对象，不能直接发送给 Helper。目标帖子的 HAR 证明页面实际请求了 `video.twimg.com` 上的 DASH 音视频分片，但已捕获的短时 `.m4s` 分片不是完整下载入口。新方案必须从页面已经取得的数据中找到完整清单或完整 MP4，而不是复制 `blob:` 地址或拼接零散分片。

本设计不承诺所有 X 帖子都能在未播放时暴露完整媒体信息。实施的第一个停止点是最小捕获探针：只有目标帖子能在不播放的情况下取得可下载来源，才允许继续修改正式协议和 Helper。

## 职责边界

### 页面主世界观察器

观察器在 `document_start` 注入 X 页面主执行环境，以便在页面应用发出媒体接口请求前安装最小包装。它只观察 `fetch` 与 XHR 返回值的副本，不取消、不重发、不改写页面请求，也不改变页面拿到的原响应。

观察范围限制为 X 自身的候选 API/GraphQL 响应。解析器递归识别视频媒体结构及 `video_info.variants` 等稳定字段形态，不依赖某一个 GraphQL 操作名、查询哈希或整份响应固定结构。

页面观察器只向扩展桥发送候选媒体描述，不负责调用 Native Messaging，也不保存 Cookie、Authorization、响应头或完整接口响应。

### 隔离世界桥

隔离世界桥把页面数据视为不可信输入，并执行以下校验：

- 当前页面必须是可解析的 `x.com/<用户>/status/<postId>` 单帖地址。
- 候选媒体必须能关联当前 `postId`。
- 媒体 URL 必须使用 HTTPS，主机必须严格为 `video.twimg.com`。
- 只接受 HLS 清单、DASH 清单或完整 MP4；拒绝 `blob:`、图片和孤立 `.m4s` 分片。
- 不保留原始响应中的其他帖子、用户或授权数据。

校验后的描述只保存在扩展内存中，以 `postId` 为键。X 的 SPA 路由切换到其他帖子时立即丢弃旧缓存；页面刷新或扩展进程退出后自然消失，不写入扩展存储。

### 后台协调器

用户点击插件后，后台读取当前活动标签页和规范化帖子地址，并向该标签页查询当前帖子的媒体缓存。若缓存尚未形成，最多等待约三秒；等待期间不触发视频播放或播放器点击。

取得完整媒体来源时，后台把帖子信息和清洗后的来源交给 Native Host。未取得完整来源时仍发送现有地址请求，让 Helper 运行当前 yt-dlp 帖子解析作为兼容降级，并把真实失败输出展示给用户。

## 媒体识别与来源选择

解析器只关心视频媒体，并按页面中的媒体顺序分组。每个视频最终选择一个完整下载来源：

1. 完整 HLS master playlist 或 DASH manifest。
2. 没有清单时，选择 bitrate 最高的完整 MP4 variant。
3. 只有 `blob:`、图片、预览图或 `.m4s` 分片时，视为没有完整来源。

不同清晰度 variant 属于同一个视频，不得变成多个下载结果。多视频帖子按页面原始顺序生成多个媒体描述。第一版不向用户提供清晰度选择，也不传递 Cookie 或请求头；如果真实捕获证明完整来源仍必须依赖额外的非敏感请求头，需暂停并重新取得范围批准。

## 最小可行性探针

正式实现前先建立边界明确的捕获探针，只用于回答一个问题：指定目标帖子在已登录的 Chrome 或 Edge 页面中、不播放视频时，初始接口响应是否包含完整 HLS、DASH 或 MP4 来源。

探针成功条件：

- 来源属于当前 `postId`。
- 来源通过 HTTPS 与 `video.twimg.com` 校验。
- 使用现有固定工具链可以据此取得完整视频，而不是只下载短时分片。

如果页面响应不可读取、初始数据只有不完整分片，或者必须播放后才出现完整来源，本阶段立即停止。不得先扩展权限、传递 Cookie、硬编码私有 API 参数或大范围修改 Helper 来掩盖可行性失败。

## Native Messaging 协议

协议升级为 v2，并保留 Helper 对当前 v1 地址请求的兼容。v2 请求表达一个帖子任务以及按顺序排列的媒体来源，概念结构如下：

```json
{
  "version": 2,
  "action": "enqueueDownload",
  "payload": {
    "postId": "2101536546898022893",
    "postUrl": "https://x.com/lvmaozhijia/status/2101536546898022893",
    "mediaSources": [
      {
        "mediaId": "2101534982368071680",
        "type": "dash",
        "url": "https://video.twimg.com/.../manifest.mpd"
      }
    ]
  }
}
```

字段名和 Codable/TypeScript 类型以实施 Plan 为准，但不得偏离以下语义：一个帖子是一条队列任务；每个视频只有一个完整来源；来源顺序就是下载顺序；请求中不存在 Cookie、Authorization、完整接口响应或页面 HTML。

## Helper 校验与下载

Helper 在任务进入下载协调器前再次执行与扩展独立的输入校验，不能信任扩展已经过滤：

- `postId` 必须与规范化 `postUrl` 一致。
- 来源必须为 HTTPS 且主机严格等于 `video.twimg.com`。
- 类型与 URL 后缀或可识别格式一致，只允许 HLS、DASH 和完整 MP4。
- 媒体数组不能为空、顺序稳定且不包含重复来源。

存在 `mediaSources` 时，Helper 跳过帖子解析，直接把每个来源交给内置 yt-dlp；yt-dlp 继续通过内置 FFmpeg 处理清单下载和音视频合并。不存在来源时沿用当前帖子地址解析。所有工具调用继续使用可执行文件路径和参数数组，不经过 Shell、不读取 PATH 或用户配置。

现有桌面命名、临时工作目录、串行队列和完整 stderr 反馈保持不变。一个帖子包含多个视频时仍是一个任务，按媒体数组顺序串行处理；任一视频失败，任务保留并指出失败序号、来源类型、退出码和完整标准错误。

## 去重与重复点击

去重键继续使用规范化帖子地址，成功下载并移除任务前都保持唯一：

- 任务处于排队、解析或下载状态时，再次点击只返回现有任务，不新增下载。
- 任务已经失败，且新请求包含经过校验的完整媒体来源时，更新原任务的来源并从同一任务重新排队，不创建第二条任务。
- 任务已经失败，而新请求仍只有帖子地址时，保持原失败状态和错误详情；手动重试与删除由后续失败恢复 Issue 实现。
- 全部视频成功移动到桌面后，才从当前内存去重集合移除。

不检查桌面既有文件，不以时间戳文件名或桌面扫描结果参与去重。

## 权限与安全边界

第一版只增加在 `x.com` 页面运行主世界和隔离世界脚本所必需的最小 Manifest 配置。不申请 `cookies` 权限，不读取 Chrome/Edge 用户目录，也不把 `webRequest` 作为首选捕获方案。若最小探针证明页面响应包装不可行，必须回到设计阶段评估替代方案，而不是静默扩大权限。

页面消息可能被站点脚本伪造，因此扩展和 Helper 两侧都必须把消息视为不可信输入。两侧的独立 URL、帖子和媒体类型校验是安全边界；页面来源身份本身不是可信凭据。

## 验证与验收边界

自动化验证聚焦纯逻辑和协议边界：

- 帖子 ID 绑定、视频媒体递归识别、variant 分组与来源优先级。
- 图片、`blob:`、孤立 `.m4s`、非 HTTPS 和非 `video.twimg.com` 来源拒绝。
- SPA 导航清除旧缓存、点击等待超时和地址请求降级。
- v1/v2 编解码、Helper 二次校验、单视频和多视频顺序。
- 同地址运行中去重、失败任务由新来源刷新以及成功后释放去重键。
- 直接来源下载参数、工具失败和完整错误传播。

自动化测试不模拟 X 的完整页面运行时，不新增假 DOM、截图、布局、焦点、指针或播放器交互测试。扩展构建及 Helper 可执行边界验证通过后，由用户在 Chrome 和 Edge 中加载稳定开发产物，验证指定目标帖子无需播放即可下载、多次点击不会重复、失败信息可见。

## 实施停止点

1. 书面 Spec 批准后创建并审核实施 Plan。
2. 先完成最小捕获探针；目标帖子未证明可行时停止，不进入正式协议修改。
3. 捕获可行后实现扩展缓存和 v2 请求，并完成纯逻辑与构建验证。
4. 再实现 Helper 直接来源下载和任务刷新，完成整体自动化验证。
5. 停在用户 Chrome、Edge 与 Helper 实际验收；验收通过不等于批准 Git Commit。
