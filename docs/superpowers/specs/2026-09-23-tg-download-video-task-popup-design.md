# TG Download 视频下载任务 Popup 架构设计

## 元信息

- 工作项：`2026-09-23-tg-download-video-task-popup`
- 状态：已批准
- 创建日期：2026-09-23
- 最近更新：2026-09-23
- 对应 Issue：[建立 TG Download 视频下载任务 Popup](../../changes/issues/2026-09-23-tg-download-video-task-popup-issue.md)

## 1. 设计目的

TG Download 的视频请求和文件写入发生在 Telegram 页面 MAIN world 中，当前页面菜单同时承担入口和下载状态显示。这个耦合使同一菜单进入忙碌状态后无法继续发起其他视频下载，也使用户关闭媒体预览后失去状态入口。

本设计将“发起下载”和“查看任务”分离：页面菜单只负责选择保存路径并发起视频任务，Popup 负责汇总展示任务状态。视频下载仍由原页面标签页执行，既不迁移到后台，也不持久化为历史记录。

## 2. 已确认的用户行为

- 只处理视频；图片保持现状。
- 用户确认系统保存路径后，下载按钮变为短暂提示，约 1.2 秒后自动淡出。
- 下载中的视频不阻止用户打开其他媒体并发起新下载。
- Popup 是唯一持续状态入口，关闭媒体预览不会影响已经开始的任务。
- 任务仅保存在内存中；下载成功立即移除，下载失败保留到用户清理。
- 不显示下载数量角标。
- 不提供取消、暂停、重试、历史记录或单项操作。

## 3. Popup 信息结构

Popup 默认尺寸为 `360 × 400px`。

```text
┌──────────────────────────────────────┐
│ 下载                    [文件夹] [清理] │
├──────────────────────────────────────┤
│                                      │
│ video-a.mp4                          │
│ ███████████░░░░░░░░░  56%           │
│                                      │
│ video-b.mp4                          │
│ ░░░░░░░░░░░░░░░░░░░  下载中         │
│                                      │
└──────────────────────────────────────┘
```

- Header 固定在顶部，左侧标题为“下载”。
- Header 右侧依次使用 `folder-down.svg` 和 `trash.svg`。
- Header 与内容区之间有一条分割线。
- 内容区填满剩余高度并独立纵向滚动。
- 没有任务时只显示居中的“没有下载任务”。
- 每行显示完整职责最小集：文件名、进度条、百分比或状态文字。
- 已知总字节数时显示百分比；未知总字节数时使用不确定进度和“下载中”。
- 失败任务显示明确失败原因，但不提供重试、取消或其他操作按钮。
- 没有失败任务时，清理按钮为不可用状态。
- 视频任务创建后不主动打开 Popup；页面提示用户可从工具栏扩展图标查看进度。

## 4. 任务状态模型

内存中只保留 Popup 需要显示的最小数据：

```text
VideoDownloadTask
├─ id：标签页内唯一任务标识
├─ filename：用户确认后的保存文件名
├─ state：downloading | failed
├─ loadedBytes：已接收字节数
├─ totalBytes：已知时为总字节数，否则为空
└─ errorCode：失败分类，用于 Popup 状态映射与控制台诊断
```

任务不保留媒体 URL、文件句柄或文件内容。`completed` 不作为可观察的持久状态：写入成功后直接删除任务并广播新快照。失败任务停止更新进度并保留在标签页内存中；清理操作只删除 `failed` 状态任务。

每个任务独立拥有其下载 Promise、文件写入器和进度回调。任务集合不提供队列调度，因此多个任务自然并发，实际资源调度交给浏览器和网络层。

## 5. 架构与职责

### 5.1 MAIN world：下载执行与事实来源

现有下载内容脚本继续负责媒体识别、系统文件保存窗口、分段请求和文件写入，并在标签页内维护视频任务集合。

- 系统保存窗口取消时不创建任务，页面菜单恢复现有可操作状态。
- 保存路径确认后创建任务、关闭菜单，再异步执行下载。
- 现有分段下载的 `loaded` 与 `total` 回调更新对应任务。
- 下载成功后删除任务；失败后将任务切换为 `failed`。
- 关闭 Telegram 媒体预览不会销毁任务集合。
- 标签页刷新或关闭会终止页面执行环境，任务及下载随之消失。

### 5.2 Isolated world：受限页面桥接

新增 isolated world 内容脚本，在页面事件和扩展 runtime messaging 之间建立桥接。MAIN world 不能直接调用扩展 runtime API，因此它通过页面内自定义事件发布经过裁剪的任务快照。

桥接只接受固定事件名和严格结构的任务数据，并重新校验：

- 任务 ID 和文件名必须是受限长度字符串。
- 状态只能是 `downloading` 或 `failed`。
- 字节数必须是有限的非负数，且 `loadedBytes` 不得在已知总大小时超过 `totalBytes`。
- 不转发媒体 URL、文件句柄、任意页面对象或页面提供的可执行命令。

桥接不缓存第二份任务状态。收到后台查询时，它只向 MAIN world 发出固定的快照请求信号，并将返回的有效快照转交后台。下行控制同样只允许一个无任意载荷的“清理失败任务”信号，MAIN world 收到后仍按自身状态过滤，只删除 `failed` 任务。

### 5.3 Background：查询聚合与特权操作

后台脚本不保存任务事实，只承担协调和特权 API：

- Popup 打开时查询匹配的 Telegram 标签页。
- 向各标签页 isolated world 请求当前快照并按标签页合并。
- Popup 打开期间转发任务变化，关闭后不需要继续维护 UI 订阅。
- 将清理失败任务命令广播给存在有效桥接的 Telegram 标签页。
- 通过 `browser.downloads.showDefaultFolder()` 打开系统默认 Downloads 目录。

为使用 `showDefaultFolder()`，Manifest 增加最小的 `downloads` 权限。这个权限只用于打开默认下载目录，不替代当前系统文件保存窗口，也不接管媒体文件下载。

### 5.4 Popup：投影状态而非拥有状态

Popup 使用 WXT 原生 HTML、TypeScript 和 CSS，不引入 React 或新依赖。

- 初始化时向后台请求聚合快照。
- 打开期间接收新快照并重新渲染任务列表。
- 文件夹按钮只请求后台打开默认 Downloads 目录。
- 清理按钮只请求删除失败任务，随后以标签页返回的新快照为准。
- Popup 关闭会销毁其 DOM 和临时订阅，但不会影响页面中的任务。

## 6. 数据流

### 6.1 创建和更新任务

```text
用户确认保存路径
  → MAIN world 创建任务并显示短暂提示
  → MAIN world 发布裁剪后的任务快照
  → isolated world 校验并转发
  → background 转发给已打开的 Popup
  → Popup 渲染任务与进度
```

进度可以高频产生，但 UI 不需要逐字节渲染。实现阶段应在任务状态层进行轻量节流或合并，只保证最终进度和状态不会丢失，避免消息洪泛影响页面下载。

### 6.2 Popup 重新打开

```text
Popup 启动
  → background 查询 Telegram 标签页
  → isolated world 返回各自最近有效快照
  → background 附加标签页身份并合并
  → Popup 一次渲染当前任务
```

任务 ID 只要求标签页内唯一。后台聚合时使用“标签页 ID + 任务 ID”作为 UI 键，避免多个标签页产生相同任务 ID 时冲突。

### 6.3 清理失败任务

```text
用户点击清理
  → Popup 请求 background
  → background 广播到 Telegram 标签页
  → MAIN world 仅删除 failed 任务
  → 各标签页发布新快照
  → Popup 更新
```

清理不是乐观更新：Popup 等待事实来源返回，确保下载中的任务不会被 UI 误删。

## 7. 错误与生命周期

- 用户取消保存窗口：不创建任务，保持当前取消行为。
- 媒体请求、分段读取或文件写入失败：任务转为 `failed`，保留 `http-<status>`、`network`、`stream` 或 `file-write` 等分类，菜单不重新出现。
- 无法取得总大小：下载继续，Popup 显示不确定进度。
- Popup 关闭：任务继续下载；重新打开后重新查询。
- Background Service Worker 被回收：不丢失事实状态；下次 Popup 打开重新向标签页查询。
- Telegram 媒体预览关闭：任务继续下载。
- Telegram 标签页刷新或关闭：页面内存、文件句柄和任务同时消失，本期不恢复。
- 文件夹 API 调用失败：保持 Popup 可用，不影响任务；实现阶段提供最小的可观察失败反馈。
- 单个标签页桥接无响应：忽略该标签页，其余标签页仍正常展示。

## 9. 验证策略

自动化验证只覆盖稳定的行为和架构边界：

- 保存路径确认后创建视频任务；取消时不创建。
- 两个视频任务可同时处于下载状态，进度互不覆盖。
- 已知和未知总大小的进度模型正确。
- 成功任务自动移除，失败任务保留，清理只删除失败任务。
- 页面事件数据校验拒绝非法状态和越权字段。
- 多标签页快照聚合使用复合键，不发生任务覆盖。
- Popup 的状态投影和按钮可用性使用纯逻辑测试，不测试像素、布局或真实指针事件。
- TG Download 完整测试、TypeScript 类型检查和 WXT 构建通过。

真实 Chrome 或 Edge 由用户验收：

- 系统文件保存窗口仍正常工作。
- 关闭媒体预览后下载继续，Popup 仍显示任务。
- 连续发起两个视频下载时并发进行且进度独立。
- Popup 尺寸、空状态、滚动、Header、图标和失败状态符合设计。
- 文件夹按钮打开 Finder 的 Downloads，清理按钮不影响下载中的任务。
- 图片行为没有变化，工具栏没有数量角标。

## 10. 明确取舍

选择“标签页内存为事实来源”，而不是后台内存或持久化存储，原因是视频下载和文件句柄本来就在页面执行环境中；这一方案能在 Popup 生命周期和 Service Worker 回收之外保留状态，同时不引入恢复下载和历史管理的额外复杂度。

代价是刷新或关闭 Telegram 标签页会中断任务。该限制与“只保存在内存中”的要求一致，并在 Popup 和验收说明中作为明确边界保留。
