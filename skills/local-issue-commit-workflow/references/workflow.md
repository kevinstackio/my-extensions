# 本地 Issue 与 Commit 工作流参考

仅在创建工作项、转换状态、准备验收或准备 Git Commit 时读取本文件。

## 事实来源优先级

1. 用户最后明确批准的目标、范围和变更。
2. 适用目录中的 `AGENTS.md`。
3. 当前 Issue。
4. `docs/changes/README.md` 工作台。
5. Commit 记录、Spec 和 Plan。
6. 本 Skill 的默认模板。

发现冲突时暂停受影响的修改，取得用户决定后同步正式文档。

## 文档职责

| 文档 | 职责 | 不应包含 |
| --- | --- | --- |
| 工作台 | 想法、唯一活动 Issue、队列、待办和完成索引 | Issue 的完整范围和验收标准 |
| Issue | 目标、范围、排除项、Todo/Sub-issues、验收标准、状态、唯一下一步 | 未经批准的新功能和虚假完成状态 |
| Commit 记录 | 预期边界、实际交付、验证、限制、用户验收、最终 Commit message 与批准状态 | 计划冒充的实际结果、Commit SHA |
| Spec | 必须作出的设计决策、边界和取舍 | 动态任务状态、完整实施步骤 |
| Plan | 实施顺序、影响模块、验证方式和停止点 | Issue 范围之外的功能、完整实现代码 |

Issue 与 Commit 记录必须同时创建、一一对应，并互相链接。Spec 和 Plan 按需创建，使用相同公共前缀关联。

## 任务规模

- 小型任务：一个用户目标，不改变公共 API、数据模型、权限、构建体系或核心架构。使用一个 Issue 和 3–6 个 Todo；通常不创建 Spec/Plan。
- 中型任务：同一交付结果包含 2–3 个有依赖的阶段。可在 Issue 内定义 Sub-issues，必要时创建 Plan。
- 架构任务：涉及跨项目公共能力、公共 API、数据模型、权限、安全、构建体系或不可逆迁移。创建必要的 Spec 和 Plan，并分别等待批准。

修改多个文件、增加测试或删除旧实现本身不构成拆分 Issue 的理由。能够独立产生价值、验收或回滚的结果应拆成新的主 Issue。

## 状态流转

```text
想法 → 已排队 → 规划中 → 待批准 → 实施中 → 待验收 → 待提交 → 已完成
```

还可使用 `已暂停` 或 `已取消`。状态必须反映仓库事实：

- `实施中`：范围已批准，正在修改或验证。
- `待验收`：约定的自动化验证已执行，等待用户观察结果。
- `待提交`：用户已经明确表示验收通过，但尚未批准 Git Commit。
- `已完成`：最终交付 Git Commit 已成功。

当前 Issue 的最终 Commit 成功前，不得开始下一个 Issue；新想法写入收件箱、队列或待办。

## Issue 必需内容

- 元信息：工作项、项目、类型、状态、当前阶段、日期。
- 背景与用户可观察的问题。
- 单一、可整体验收的目标。
- 明确的范围和排除项。
- 3–6 个 Todo，或 1–3 个真正有依赖的 Sub-issues。
- 可观察、可复现的验收标准。
- 与 Commit 记录及可选 Spec/Plan 的链接。
- 唯一下一步。

Todo 创建时使用 `- [ ]`，实际完成且验证后改为 `- [x]`。

## Commit 记录必需内容

- 元信息及唯一对应 Issue。
- 预期交付边界。
- 实际完成内容。
- 验证命令和实际结果。
- 未验证事项与限制。
- 用户验收结果。
- 最终 Commit message。
- 最终提交批准状态。

初始记录中的实际结果、用户验收、Commit message 和批准状态必须保持待填写或未批准，不得预写成功结论。

## 阶段验收

阶段报告必须说明：

1. 本阶段实际完成了什么。
2. 自动化验证命令和实际结果。
3. 尚未验证的事项和限制。
4. 用户需要执行的操作。
5. 按用户可观察结果描述的复现步骤和预期结果。

用户没有明确表示验收通过时，保持 `待验收`。用户要求“提交代码”不能自动解释为验收通过；先完成验收确认，再单独申请 Git Commit 批准。

## 最终提交

最终审批请求列出：

- 所有待提交文件；
- diff 摘要；
- 验证结果；
- 未验证事项；
- 完整 Commit message；
- 即将执行的机械性终态更新。

批准后只允许执行已列出的终态更新。任何其他文件或 diff 变化都会使批准失效，需要重新展示并批准。

一个 Issue 原则上对应一个最终交付 Git Commit。Commit message 使用：

```text
<type>(<scope>): <中文动作与结果>

- <实际结果一>
- <实际结果二>
```

允许的 `type`：`feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`build`、`ci`、`perf`、`revert`。标题末尾不加句号，正文使用 1–3 条中文项目符号。

## 常见错误

| 错误 | 正确处理 |
| --- | --- |
| 先改代码，之后补 Issue | 删除未获批准的实施性修改或先停下，取得范围批准并建立记录 |
| 只有 Issue，没有 Commit 记录 | 同步创建同名前缀记录并互相链接 |
| 测试通过就写“已验收” | 保持 `待验收`，等待用户明确确认 |
| 用户说验收通过后直接提交 | 更新为 `待提交`，展示最终审批材料并再次等待批准 |
| Commit 前提前写“已完成” | 只在最终批准覆盖的机械性更新中修改，并在提交失败时恢复 |
| 为不同文件创建多个 Issue | 按独立用户价值、验收和回滚边界判断，不按文件数量拆分 |
| Skill 保存当前活动 Issue | 每次从目标仓库工作台读取动态状态 |
